## Context
We have been attempting to replicate a highly polished, responsive Character Select UI based on a Figma design. Initially, the UI was built procedurally via C# code (instantiating GameObjects and adding RectTransforms on the fly). This proved too brittle and verbose. 

We attempted to pivot to an **Atomic Prefab** architecture to separate logic from visuals, but because the user didn't have time to build the prefabs manually, the AI attempted to generate the prefabs and wire the scene using C# Editor Scripts. **This failed visually.**

## Summary of Recent Work
1. **View Scripts Created:** Built clean, atomic data-binding scripts (`UiAbilityCardView.cs`, `UiClassCardView.cs`, `UiEquipSlotView.cs`, etc.).
2. **Controller Refactored:** Stripped 300+ lines of procedural layout code from `CharacterSelectController.cs`. It now accepts prefab references and simply calls `Instantiate()` and `.Bind()`.
3. **Automated Assembly Attempted:** Wrote Editor scripts (`UiPrefabBuilder2.cs` and `WireMenuScene.cs`) to dynamically generate the UI Canvas and Prefabs in the `Bootstrap` scene.
4. **Current Result:** The logic works, but the visual layout is fundamentally broken. RectTransforms are squished, LayoutGroups are misconfigured, and the custom styling (SDF shaders, fonts) didn't translate well via blind code generation.

## UI Approaches: Pros & Cons

### 1. Procedural UGUI (Code-Driven GameObjects)
*Building RectTransforms, Image components, and LayoutGroups entirely via C# at runtime.*
* **Pros:** Everything is in source control. No merge conflicts in Unity scenes/prefabs. Fast for pure logic developers.
* **Cons:** **An AI's nightmare.** AI agents cannot "see" the game view. Guessing RectTransform anchors, pivots, and layout math blindly results in horrible, broken layouts. The code becomes massively bloated with UI boilerplate.

### 2. Atomic Prefabs (The Current Attempt)
*Creating `UiCard.prefab` in the Editor, attaching a `UiCardView.cs` script, and instantiating it at runtime.*
* **Pros:** Industry standard for UGUI. Clean separation of concerns. Designers can tweak pixels in the Editor while coders handle the logic.
* **Cons:** **Requires manual human assembly.** AI cannot easily or reliably generate Unity Prefabs. Trying to automate the creation of these prefabs via Editor scripts leads to the exact same visual issues as the procedural approach.

### 3. UI Toolkit (UXML / USS)
*Unity's modern UI system, functioning identically to HTML/CSS (Web Design).*
* **Pros:** **The holy grail for AI UI generation.** Because it uses text-based markup (UXML) and Flexbox styling (USS), an AI can effortlessly generate pixel-perfect, responsive layouts without ever opening the Unity Editor. 
* **Cons:** Requires a paradigm shift. UGUI components (`Button`, `Image`, `Text`) must be replaced with `VisualElements`. The existing `Ui*View.cs` scripts would need to be rewritten to query the UXML tree instead of using `[SerializeField]`.

## What Needs to be Solved Next

**Decision Point:** The next agent needs to decide whether to stick with UGUI or migrate to UI Toolkit.

**Path A: Stick with UGUI (Requires Human Time)**
1. Delete the `MenuCanvas` from the `Bootstrap` scene.
2. Delete the broken prefabs in `Assets/_Game/Prefabs/UI/`.
3. The human developer **must** build the UI prefabs visually in the Unity Editor.
4. Attach the existing `Ui*View.cs` scripts to those new prefabs and drag the references into `CharacterSelectController`.

**Path B: Migrate to UI Toolkit (Can be fully automated by AI)**
1. Delete all `Ui*View.cs` scripts and remove the `MenuCanvas`.
2. The AI writes a `CharacterSelect.uxml` file defining the layout hierarchy.
3. The AI writes a `CharacterSelect.uss` file using Flexbox to style the layout perfectly based on the Figma design.
4. Refactor `CharacterSelectController.cs` to use a `UIDocument` and bind logic to the `VisualElements`.
